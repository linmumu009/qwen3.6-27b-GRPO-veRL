# Step 120 长上下文单请求吞吐阶梯（2026-08-14）

## 结论

在 huawei-06 的单个 TP8 vLLM 引擎上，以并发 1、固定生成 256 tokens、关闭 prefix caching 的受控条件测量后，**没有观察到 40K 后解码速度降到原来的 1/10**：

- 2K 总上下文的单序列解码速度中位数为 `9.331 tokens/s`；
- 40K 为 `9.121 tokens/s`，保留 2K 基线的 `97.75%`；
- 48K 为 `9.190 tokens/s`，保留 2K 基线的 `98.48%`；
- 40K 和 48K 相对 16K/32K 两档均值分别为 `99.29%` 和 `100.03%`。

长度增长主要反映在首 token 等待时间（TTFT）：从 2K 的 `0.300s` 增至 40K 的 `3.625s` 和 48K 的 `4.318s`。固定生成 256 tokens 时，包含 prefill 的端到端吞吐从 `9.266 tokens/s` 降至 `8.106/7.983 tokens/s`，仍保留基线的 `87.48%/86.16%`，也不存在 10 倍下降。

## 固定条件

- 模型：Step 120 HF 导出；vLLM 0.18.0；BF16；TP8；Ascend；
- 并发：1；每档 2 次重复，另有 1 次不计入结果的短请求预热；
- 生成：固定 256 tokens，`temperature=0`，`ignore_eos=true`；
- 缓存：prefix caching 关闭；chunked prefill 开启；最大 batched tokens 为 16,384；
- 输入：重复的中性 token ID，只用于形成精确长度；不保存提示或生成文本；
- 解码吞吐：`(生成 token 数 - 首 token) / 首 token 后耗时`；
- TTFT：请求开始至第一个流式 token 的时间。

两次重复之间的最大相对极差为 `1.70%`。运行完成后基准进程已退出，抽查 NPU 利用率恢复为 `0%`、HBM 占用为 `4%`。

## 证据边界

本结果可以否定“该模型在这台机器、单请求条件下一过 40K 就只剩 1/10”的说法，但不能直接代表高并发服务总吞吐。此前日志中的 `400–500 generation tokens/s` 是多序列合计服务吞吐，本报告的约 `9.2 tokens/s` 是单条序列解码速度，两者不可直接比较。

若需要验证“高并发且 KV cache 接近满载时是否在 40K 后坍塌”，还需另做固定并发与固定活跃 token 预算的负载阶梯；该实验会明显增加资源占用，本轮未执行。

原始非内容结果见 [`long_context_decode_benchmark_step120_20260814.json`](long_context_decode_benchmark_step120_20260814.json)，其中只包含 token 数、时延、吞吐和测量合同。
