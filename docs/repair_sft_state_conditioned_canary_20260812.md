# 状态条件化 SQL 恢复金丝雀（2026-08-12）

## 结论

完整训练前门禁、一步训练和训练后便宜门禁已经完成，候选不进入回放，也不追加训练。

把 Step 120 的首个错误 SQL 及其实际工具结果加入零-loss 上下文后，纠正 SQL 的教师 NLL 在 `16/16` 题上改善，均值从 `1.6815` 降到 `1.4118`（`-16.04%`）。329 个纠正 SQL token 的 greedy 命中从 `221` 增到 `225`，top-5 从 `284` 增到 `298`，平均 rank 从 `20.12` 降到 `16.72`。这说明“覆盖模型实际错误状态”的方向有效。

但模型仍没有越过预注册决策边界：逐题纠正 SQL 几何平均概率超过 `0.5` 的数量保持 `1/16`，要求至少 `12/16`；整段纠正 SQL 全部 greedy 仍为 `0/16`。因此没有运行原始 prompt 非退化诊断、三次工具调用短回放、48K 完整回放、held-out 或老板完整评分。

## 新的全查询基线

首条 SQL `0/16` 并不代表后续完全无法恢复。只读扫描全部查询后：

| 模型 | 查询总数 | 前 2 条获得正确/等价证据 | 前 3 条 | 任意位置 |
| --- | ---: | ---: | ---: | ---: |
| Step 120 | 167 | 2/16 | 3/16 | 4/16 |
| 通用 SFT Step 5 | 235 | 1/16 | 2/16 | 4/16 |
| SQL-weighted Step 1 | 181 | 1/16 | 3/16 | 5/16 |

因此下一次自由策略门禁应以“前三条内首次得到正确证据”为主指标，同时报告首条命中；不能只用首条，也不能用大量后续查询换来的任意位置命中掩盖效率退化。

## 数据、训练与 checkpoint

- 16 条样本全部来自 train236 同题开发门禁；不涉及 held-out。
- 第 0 个 assistant 回合是 Step 120 首错 SQL，实际工具结果紧随其后；两者只作为上下文，loss 严格为 0。
- 只监督第 1 个 assistant 的机械验证纠正 SQL 和第 2 个 assistant 的最终答案，权重继续固定为 `0.25/8/1`。
- 16 条样本为 `1608–7604` tokens；除最长一条外其余 15 条不超过 `2441`。训练上限冻结为 `8192`，`truncation=error`。
- 一步训练退出码 `0`，墙钟约 `334s`；loss `1.637145`、grad norm `73.0647`、学习率 `1e-6`。
- 单卡峰值 allocated HBM `26.59 GiB`，整机 CPU 内存 `796.50 GiB`。
- 最终 checkpoint 含 32 个模型 distcp 主分片，约 `51 GiB`；内容为 `model,extra`，optimizer state 文件为 0。
