## 四次启动与问题修复

### `-01`：val-only 仍创建完整优化器

冻结评测虽然设置了 `val_only`，veRL 的 Megatron actor 仍初始化完整 Adam，并尝试把优化器状态卸载到锁页主机内存，导致 step 0 主机内存申请失败，尚未产生轨迹。

修复：冻结基线显式启用 Megatron `forward_only`，关闭 optimizer/gradient offload，不创建梯度、Adam 或 checkpoint；正式训练路径不受影响。

### `-02`：Fastest-K 补丁错误假定所有配置都有 `async_training`

模型、两套 TP8 vLLM 和四工具已初始化，但标准 One-Step/val-only 配置没有 `async_training` 字段，历史 Fastest-K 补丁直接读取该字段，在 0/200 处抛出配置错误。

修复：只有存在 fully-async 配置且显式启用时才激活 Fastest-K；标准评测自动关闭，并补齐旧 marker 到新补丁的前向幂等升级。

### `-03`：冻结基线重复进行首次全量权重同步

actor 与 rollout 都从同一只读基础模型加载，却仍执行 1→16 actor-to-rollout 全量广播。模型和 944/944 权重转换均完成，但首次广播超过 60 分钟仍未进入 1/200，造成无意义等待。

修复：仅在 `val_only=True`、`resume_mode=disable` 且 actor/rollout 使用同一基础模型时跳过首次同步。训练、checkpoint 恢复及非 val-only 路径继续保留同步。

### `-04`：成功完成，但暴露全量批处理长尾和 DP 失衡

修复后成功进入完整 PI rollout，并完成 200/200。运行中后段曾观察到一个 TP8 副本已排空而另一个副本仍有大量长轨迹；veRL 要等整个 200 条验证批次完成后才统一写出结果，因此中途看不到局部结果，最后阶段也无法把已空闲副本用于接管另一副本的剩余任务。

这不是正确性失败，但会显著降低评测效率。后续训练不应照搬“200 条一次性 barrier”的执行方式；应使用已经验证过的 bounded fully-async 完整 GRPO group 队列，并增加按任务完成动态补充、逐轨迹可观测性和受控超时。
