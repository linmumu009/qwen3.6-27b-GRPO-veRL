# 原生 Qwen3.6-27B 与 Step 120 的代理奖励错配归因

日期：2026-08-12  
结论（2026-08-12 证据更正）：**相同首错状态的 forward-only 概率对照仍证明核心 SQL misranking 在原生模型中已经存在，不是 Step 120 新制造的。此前同 16 题的 Step 120 自由回放因 vLLM 没有同步 checkpoint 权重而撤回，不能再用于判断自然行为是否被训练放大。** 更准确的称呼是“代理奖励错配/高过程分错答模式”，而不是已经证明模型具有主观意图的“奖励黑客”。

## 1. 归因问题

此前 Step 120 出现两个容易被误读为训练诱发奖励黑客的现象：

- 老板过程指标较高，但最终数值经常错误；
- 在首个错误 SQL 及其真实工具结果之后，模型对实际错误 SQL 的 semantic delta 概率高于机械正确 SQL。

仅观察训练后 checkpoint 无法判断这些问题是基础模型原有，还是训练创造/放大的。因此本轮设置两个互补对照，并且都只做前向评估：

1. **相同状态概率对照：** 原生模型与 Step 120 读取完全相同的 16 个 Step 120 首错状态、相同 chosen/rejected SQL 和相同 semantic masks。该对照只改变模型权重，回答条件偏好是否由训练产生。
2. **自然行为对照（待重跑）：** 原计划让原生模型与 Step 120 在相同 16 题、相同 prompt、greedy n=1、老板四工具、48K 上下文和 25 个工具反馈批次下各自自由生成。后续日志审计发现 Step 120 侧跳过 actor→vLLM 初始权重同步，故该对照没有真正改变 rollout 权重，证据已撤回。

两组任务都是反复用于诊断的开发题，不作 held-out 泛化声明。

## 2. 相同错误状态下的概率归因

margin 定义为 `rejected mean NLL - chosen mean NLL`；正值表示模型偏好机械正确 SQL，负值表示模型偏好 Step 120 实际首错 SQL。

| 指标 | 原生模型 | Step 120 | Step 120 - 原生 |
| --- | ---: | ---: | ---: |
| 正确候选占优 | 0/16 | 0/16 | 0 |
| 平均 margin | -1.2057 | -1.1877 | +0.0180 |
| 中位 margin | -1.1468 | -1.1270 | +0.0199 |

逐题比较中，Step 120 相对原生有 `12/16` 朝正确方向移动、`4/16` 朝错误方向移动；平均绝对变化只有 `0.0290`，没有任何一对跨过 0。

按首分叉家族，两个模型的结论也一致：

| 家族 | 原生平均 margin | Step 120 平均 margin | 两者正确候选占优 |
| --- | ---: | ---: | ---: |
| aggregation | -1.1638 | -1.1459 | 均为 0/9 |
| query start | -1.9037 | -1.8726 | 均为 0/3 |
| identifier/literal | -0.9864 | -0.9744 | 均为 0/3 |
| clause | -0.1469 | -0.1492 | 均为 0/1 |

这项只改变权重的对照给出直接归因：**正确/错误 SQL 的核心条件偏好在原生模型中已经存在；Step 120 没有创造它，也没有在均值上放大它。**

## 3. 同 16 题自然自由回放：证据撤回

旧运行虽然完整落盘并经老板原版评分器打分，但 actor 加载分布式 checkpoint 后，Ray 内的 rollout task 明确打印了跳过初始权重同步。vLLM 因此仍使用原生模型权重，旧表中标作“Step 120”的自然轨迹不具备该权重身份。

旧数值只作为故障现场保留，不再支持以下主张：

- 不再声称 Step 120 自然回放有 `12/16` 个 `result_wrong_process_ok`；
- 不再声称 Step 120 相对原生为 `1 胜 / 4 负 / 11 平`；
- 不再声称 Step 120 没有放大重复命令、未收尾或高过程分错答。

修复后的启动器把同步开关放入可序列化 trainer config，并要求运行日志出现明确 force 标记、不得出现 skip 标记。只有以该合同重跑完整 16 题后，才能恢复自然行为归因。

## 4. 可以下什么结论

### 已验证

- 核心 SQL misranking 是原生预存缺陷：原生和 Step 120 都是正确候选 `0/16` 占优，margin 几乎重合。
- 原生自然回放本身确认高过程分错答可以在项目训练之前出现；但真实 Step 120 的完整自然发生率、重复命令和完成率尚未获得有效对照。
- 老板总奖励可在原生模型仅 `3/16` 数值正确时达到 `0.7813`，说明奖励本身对过程代理给分过强，不能把总奖励当作准确率替代指标。

### 不能下的结论

- 不能用已撤回的自由回放声称 Step 120 没有放大自然行为；该问题必须在强制同步检查通过后重跑。
- 不能把模型意图称为已证明的“欺骗”或“主动钻奖励漏洞”。现有证据证明的是结果指标与过程代理脱钩，以及训练前就存在的模型能力缺口。
- 不能用本 16 题估计总体发生率或泛化差异；它们是开发诊断集。

## 5. 下一步决策

下一步不应把问题简化成“撤销训练即可解决”，因为原生模型更明显地表现出相同模式。优先级应改为：

1. 模型选择和训练门禁以机械数值正确/可验证 SQL 证据为主指标；过程分只能作辅助解释，不能补偿错误结果。
2. 将 `result_wrong_process_ok` 设为显式反指标或硬门禁，避免错误答案仅凭表/字段覆盖获得高分。
3. 以强制同步 marker 为前置条件，重跑原生、Step 120 与未来 checkpoint 的固定同题归因面板，分别报告正确率、过程分、错误且过程 OK、重复命令和完成率。
4. 训练目标仍聚焦 plan-to-SQL grounding/realization，但下一批训练 pairs 必须与当前 16 题不重叠，并用独立 held-out 检验；不能继续在当前 16 对上加步数。

有效的相同状态评估未初始化 optimizer、未保存 checkpoint。撤回的自然回放也未训练模型，但不能作为 Step 120 权重证据。
