# 面向领导的技术实验汇报方法论

日期：2026-08-06

## 适用场景

用于把模型训练、评测、奖励设计等技术结果整理成简短的领导汇报。默认目标不是完整复盘技术细节，而是在较短时间内讲清楚：做成了什么、取得了什么提升、为什么还有差距、下一阶段准备做什么。

## 核心原则

1. **成绩优先，但不改变事实口径。** 先讲已经跑通的工程链路和确认的能力提升，再讲整体指标未提升的原因。
2. **区分“能力提升”和“能力转化”。** 过程能力提升不等于最终结果提升；如果模型学会了更好的过程，但没有完成收尾，应明确说瓶颈在能力转化。
3. **数字服务结论。** 只保留能支撑核心判断的数字，不展示审计级精度，不让领导从一串小数中自己找结论。
4. **不同评测口径不能混用。** 整体结果、特定子集结果、过程分、结果分和总奖励必须分别说明，不能把条件性提升写成整体提升。
5. **下一步使用执行口吻。** 写“下一阶段计划”或“下一阶段重点”，不写“我建议”；只列真正准备实施的事项，不为了显得完整而扩写过多动作。

## 默认四段结构

### 第一段：背景与完成情况

用一段话回答：

- 在什么模型和上下文规模上训练；
- 使用什么训练方式和数据；
- 是否完成预定步数；
- 哪些关键链路已经跑通。

推荐顺序：`模型规模 → 上下文/工具环境 → 训练方式和步数 → 数据来源 → 端到端完成情况`。

示例句式：

> 这次我们在【模型】上完成了【上下文和工具环境】下的【训练方式】，并跑完【步数】。训练使用【数据来源】，目前【训练、奖励、重放、复评】链路已经完整跑通。

第一段只交代背景，不提前展开指标、问题或建议。

### 第二段：结果与奖励有效性

先讲正向结果，再讲整体差距，最后给出奖励是否有效的判断。

推荐顺序：

1. 过程能力从多少提升到多少；
2. 关键正确率或命中率从多少提升到多少；
3. 条件性结果必须先说明适用范围，例如“在两轮都完整收尾的共同任务上”；
4. 再说明整体结果分或总奖励的真实变化；
5. 用这些现象解释奖励是否容易被刷分。

奖励有效性的推荐表述：

> 奖励没有因为模型查表更多、输出更长或过程分更高就被轻易刷高；缺少最终回答时仍会被硬门控归零。结合在线奖励与离线重放一致的结果，目前没有发现明显的 reward hacking。

不要写“已经证明完全抗 reward hacking”。现有证据通常只能支持“目前没有发现明显问题”。

### 第三段：原因分析

用少量行为指标解释为什么“过程变好，但整体结果没有同步变好”。结构应为：

`行为变化 → 直接后果 → 指标变化 → 当前瓶颈`。

示例：模型查表和推理更积极，SQL 数量和回答长度增加，但部分轨迹没有及时结束探索并给出最终回答，导致完整收尾率下降。因此，主要瓶颈不是模型没有学到能力，而是终止策略和最终回答能力没有同步跟上。

原因分析只保留两到三个最能解释问题的行为指标，不罗列所有可观测字段。

### 第四段：下一阶段计划

使用明确、可执行、可验证的计划。默认保留两到三项核心动作，每项说明“做什么”和“要验证什么”。

本项目当前优先表述为：

1. 在保持 48K 上下文和其他配置不变的情况下，适当增加训练步数，观察模型能否逐步学会在上下文预算内完成探索并给出最终回答。
2. 对比奖励模型与当前规则奖励策略，尝试进一步优化奖励策略；通过离线重放和短程 A/B 判断奖励模型能否更准确地区分有效探索、无效重复和最终答案质量。

除非已经确定要执行，否则不要自动增加数据扩充、终止机制、部署或其他计划，以免把讨论方向写成既定承诺。

## 数字表达规则

1. 小数最多保留三位，例如 `0.671 → 0.765`，不使用 `0.670625 → 0.765000`。
2. 百分比通常保留一位或直接使用整数，例如 `15.9%`、`10% → 15%`。
3. 比率变化用“百分点”：`10% → 15%，提高 5 个百分点`。
4. 相对变化用“提升/下降百分之多少”：`0.612 → 0.709，提升 15.9%`。
5. 重要指标优先写“从 A 到 B”，不要只写“提高了多少”，让听众能判断起点和终点。
6. 同一个指标不必同时堆叠原值、绝对差、相对差三种表达。核心指标可保留三者，次要指标只保留起点、终点和方向。
7. 整体指标和子集指标必须标明范围，特别是“完整收尾任务上的提升”不能省略限定条件。
8. 面向外部或非项目成员时，不披露验证集具体规模、逐题 ID、服务器路径、文件哈希和内部数据文件名。

## 语言与语气

- 使用团队和执行口吻：“我们完成了”“下一阶段计划是”。
- 避免犹豫式表达：“我建议”“可以考虑”“也许可以”。
- 避免防御式表达：“训练不是没有提升”。直接说“过程能力有明确提升”。
- 技术词只保留决策所需部分；英文缩写首次出现时应能从上下文理解。
- 不回避负面指标，但要紧接原因和可执行方向。
- 不把“工程跑通”“奖励有效”“能力改善”“质量收敛”混为一个结论。

## 常见错误

1. **精度过高：** 六位小数更像审计表，不像领导汇报。
2. **只报增量：** 只说“提高 5 个百分点”，没有起点和终点。
3. **口径偷换：** 把完成任务子集的提升说成整体提升。
4. **过度承诺：** 把“目前未发现 reward hacking”写成“已经证明抗 reward hacking”。
5. **结论顺序错误：** 一开头先讲失败、限制和技术细节，成绩被埋在后面。
6. **行动项过多：** 自动补出一长串下一步，稀释真正优先级。
7. **口吻过弱：** 使用“我建议”，让已形成的计划听起来仍在等待决定。

## 可复用模板

> 这次我们在【模型】上完成了【上下文、工具环境】下的【训练方式】，并跑完【步数】。训练使用【数据来源】，目前【关键链路】已经完整跑通。
>
> 从效果上看，【过程指标】从【A】提升到【B】；【关键正确率/命中率】从【A】提升到【B】。在【明确限定的可比范围】内，【总奖励】从【A】提升到【B】。另一方面，整体【结果指标】从【A】变化到【B】。这一结果说明【奖励有效性判断】，目前【谨慎的 reward hacking 结论】。
>
> 训练后模型在【正向行为】上有所增强，但【探索或行为代价】也随之增加，导致【完成率或结果指标】下降。因此，当前主要瓶颈是【能力转化问题】，而不是【容易被误解的结论】。
>
> 下一阶段计划：第一，【动作及验证目标】；第二，【动作及验证目标】。完成后再根据【同口径评测】决定是否扩大训练步数、数据或方案范围。

## 输出前检查

- 第一段是否只讲背景和完成情况？
- 第二段是否先讲成绩，并明确每个提升的起点、终点和适用范围？
- 是否区分过程分、结果分、总奖励和条件性子集？
- 所有小数是否最多三位？
- 百分比变化是否正确使用“百分点”或相对百分比？
- reward hacking 结论是否保持为“目前未发现明显问题”？
- 第三段是否形成“行为—后果—瓶颈”的因果链？
- 下一阶段是否只保留真实准备执行的两到三项计划？
- 是否移除了不适合对外披露的样本规模、任务 ID、路径和哈希？
