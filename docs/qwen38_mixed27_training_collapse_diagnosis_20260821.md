# Qwen3.8 mixed27 四次曝光训练退化诊断

## 结论

这次不是服务器、超时、checkpoint 转换或评测完成率造成的假退化。最符合现有证据的解释是：**当前 GRPO 目标在正确性信号极稀疏时，仍对大量“八条全错”的组按流程代理分产生梯度；同时训练关闭了固定参考模型 KL 和熵约束，27 道窄数据又被完整重复四次，于是许多小的代理优化更新累计成了对 Step70 通用能力的漂移。**

`banded-v2`没有直接把错误答案排到正确答案上方：42条正确轨迹平均奖励为`0.7130`，822条错误轨迹为`0.1759`。问题在于108个组中只有30个出现过正确答案，另有78个组八条全错；这78个全错组全部仍有非零奖励方差。54个优化步中26步的两个组都没有任何正确轨迹。训练日志实际记录到的25个此类步骤全部产生非零梯度，平均梯度范数`1.7212`，不低于含正确轨迹步骤的`1.5090`。模型近一半更新因此完全没有“哪个答案正确”的组内依据。

建议维持当前结论：拒绝`global_step_54`，不再沿用`27×4 + reference-free + fully-async staleness=2`配方追加训练，也不把sealed6回流训练。下一次从已验证Step70重新开始，只做1–5步小金丝雀，并同时改变训练门、KL锚和评测频率。

## 发生了什么

### 训练过程本身看起来稳定，但稳定的是代理目标

| 训练观测 | 结果 | 含义 |
|---|---:|---|
| 轨迹完整性 | 54文件、864条、108组；无缺步 | 工程数据完整 |
| 唯一题目 / 每题曝光 | 27 / 4次 | 数据面很窄 |
| 严格正确轨迹 | 42/864（4.86%） | 二值正确性很稀疏 |
| mixed组 | 30/108（27.78%） | 只有这些组同时看到了对与错 |
| 全错组 | 78/108（72.22%） | 大部分组没有正确性排序依据 |
| 全错但有奖励方差 | 78/78 | 每个全错组仍会产生相对优势 |
| 两组均全错的优化步 | 26/54（48.15%） | 近一半更新纯由错误答案间代理差异驱动 |
| SQL证据正确 | 0/864 | 设计中的高质量中间证据通道实际未激活 |

训练的四次曝光没有显示训练题正确率持续崩塌：四轮分别出现`9、10、12、11`条正确轨迹，mixed组为`7、6、10、7`，平均奖励也稳定在`0.1993–0.2061`。按每9步分箱，最后9步反而有9条正确轨迹，高于最初9步的7条。

这说明最终模型并不是在这27道训练题上逐步“全不会了”。更像是模型仍能维持窄训练池上的表现，同时在未训练的同类题上发生干扰或遗忘。平均reward、局部PPO KL和训练题采样看起来平稳，因而没有在训练日志中报警。

### sealed6 是强负向信号，不太可能只由抽样运气解释

| 同一道sealed6 | 训练前Step70 | 训练后Step54 |
|---|---:|---:|
| 至少一次正确的题 | 6/6 | 1/6 |
| 正确完整轨迹 | 6/31 | 1/31 |
| 完整轨迹 | 31/32 | 31/32 |
| 超时 | 1 | 1 |
| runtime error | 0 | 0 |

完成数、超时数和runtime error完全相同，所以这不是30分钟超时范围、排队等待、服务失败或提前停止口径变化造成的。超时仍覆盖vLLM准入、生成与工具执行全过程；本轮确实吸取了此前等待时间没有计入超时的教训。

作为敏感性分析，若用训练前每题观测成功率不变来预测下一次最多6次采样，“6题中至多1题出现成功”的概率在几种简单MLE/Jeffreys/均匀先验模型下约为`0.36%–1.17%`。这不是正式总体显著性检验：sealed6是从已知mixed题中密封的条件样本，而且只有6题；但它足以说明“纯随机波动”不应作为默认解释，也足以拒绝checkpoint。

## 根因链

### 1. 全错组仍在优化流程代理，是最直接的机制

`banded-v2`把eligible且有最终答案、但最终答案和SQL证据都错误的轨迹放在`0.10 + 0.20 × process_quality`区间。这个设计保证错误上限低于正确下限，适合mixed组；但GRPO按同一prompt组内标准化奖励，在八条全错时看不到跨band的正确性差异，仍会奖励以下代理项：是否给出较长的最终回答、是否命中表、任务形态、过程完整性和较少命令等。

在822条错误轨迹内，总奖励与`base_score`相关系数为`0.9440`，与boss reward为`0.9297`，与boss result score为`0.7866`，与bash命令数为`-0.5145`。这些代理并非毫无价值，但它们不能证明答案正确。全错组全部有方差意味着这种代理排序不是偶发边角，而是主要训练信号。

日志进一步闭环：53个更新有完整指标记录，第一个更新未单独发出指标；其余25个“本步零正确”记录全部`grad_norm>0`。这些步平均局部PPO KL为`0.000586`，与含正确轨迹步骤的`0.000580`几乎相同，说明优化器并没有因为缺少正确答案而自动停止。

### 2. 小的局部KL不能替代固定Step70锚

本轮入口明确设置：

- `algorithm.use_kl_in_reward=False`
- `actor_rollout_ref.actor.use_kl_loss=False`
- `actor_rollout_ref.actor.entropy_coeff=0`

日志里的`actor/ppo_kl`约`0.000583`是当前PPO更新相对采样旧策略的局部变化指标，不是最终模型相对初始Step70的距离。每步变化很小，连续54步仍可朝同一代理方向累计漂移；因此“KL一直很小”不能证明模型没有遗忘。

这个解释也与现象一致：训练池四轮正确轨迹没有下降，但未见过的sealed6明显下降。若是单纯学习率爆炸或数值不稳定，更常见的是训练侧reward、长度、KL、梯度或完成率同步失控；这里没有这种模式。

### 3. 27题四次曝光放大了单一方向更新

27个唯一prompt完整重复四次，且每次是全参数更新。它不等价于108个独立任务。四次曝光中每轮仍有17–21个全错组，说明重复并没有持续把这些任务变成mixed，反而多次重复了相同任务分布上的代理梯度。

因此“每题用更多次”并不是免费增加训练量：当某题真实成功概率很低时，曝光次数增加主要增加全错组数量。当前数据证明4次已经过量；若改成10次，按相同结构只会进一步放大风险。

### 4. SQL证据通道实际为零，削弱了中间反馈

864条轨迹平均每条检查`16.72`个候选SELECT，gold SQL验证率100%，verifier error为0，但`sql_evidence_correct=1`一次都没有，包括42条最终答案正确的轨迹。这不像运行时故障，更可能是当前“单条候选SQL结果必须与gold结果严格等价”的证据定义无法覆盖模型通过多条探索查询、后处理或人工汇总得到正确最终答案的路径。

所以banded四档在这次训练里实际退化成主要两档：最终答案正确档和普通错误档，最高的“最终答案+SQL证据都正确”档从未出现。不能直接放宽SQL verifier，否则会重新引入奖励黑客；应先用历史轨迹离线回放设计可验证的多查询/组合证据口径，并要求错误轨迹假阳性为零或接近零。

### 5. fully-async陈旧轨迹是放大器，但现有证据不能把它定为唯一根因

本轮允许`staleness_threshold=2`且关闭rollout correction。日志末累计处理566条非当前版本轨迹，超过阈值丢弃为0；按864条总轨迹计约65.5%来自非最新参数版本。PPO clip fraction平均仅`0.00141`，说明这些样本没有大量触发clip，但陈旧数据仍会增加更新噪声并弱化“当前模型—当前奖励”的闭环。

由于没有同步或`staleness=0`的同数据对照，不能声称异步陈旧性单独造成sealed退化。它应在下一个短金丝雀中先关闭，以减少变量和提高因果可解释性。

### 6. 只保存最后模型不是根因，但让损失扩大且无法止损

训练禁用了sealed验证，只在第54步保存一个model-only checkpoint，未保存optimizer。即使质量在第5、10或20步已经下降，本轮也无法自动停止、选择较早checkpoint或从早期状态精确恢复。这不会解释为什么模型退化，却解释了为什么我们直到9.5小时训练结束后才看到问题，并且没有可回退的中间产物。

## 竞争解释审查

| 假设 | 证据 | 判断 |
|---|---|---|
| 工程失败、超时口径或评测服务异常 | 前后均31/32完整、各1超时、0 runtime error；训练与checkpoint门完整通过 | 排除 |
| 奖励把错误答案排到正确答案上面 | 正确均分0.7130，错误均分0.1759，band不重叠 | 排除这种简单形式 |
| 全错组代理优化 + 无固定KL锚 | 78/108组全错且全部有方差；25/25个有日志的零正确步骤产生梯度；KL锚关闭 | 最有证据的主机制 |
| 27题四次曝光导致窄域干扰/遗忘 | 训练四轮正确数稳定，sealed同题明显下降 | 高可信促成条件 |
| fully-async陈旧性 | 累计566条非当前版本轨迹，correction关闭 | 中等可信放大器，未单独识别 |
| sealed6纯随机波动 | 简单不变能力模型下该结果约0.36%–1.17%；但样本是条件选择且仅6题 | 不足以解释全部现象 |
| 学习率爆炸或数值不稳定 | 局部KL、clip、长度、reward无失控趋势 | 不支持 |

## 下一步：最快且能回答因果问题的实验

不要直接重跑70+18，也不要拿18或27继续滚雪球。建议回到已验证Step70，做一个最多5步的可止损金丝雀：

1. **训练门改为mixed-correct only。** 一个8响应组只有同时含至少1条严格正确和1条严格错误才允许进入GRPO更新；全错、全对、无最终答案或不安全组直接丢弃/补采，不允许按流程代理分更新。
2. **启用固定Step70参考KL。** 预注册KL目标与停止阈值；同时保留局部PPO KL，但明确区分“相对rollout旧策略”和“相对初始Step70”。
3. **金丝雀先同步或`staleness=0`。** 最多2组×8响应/步、1–5步，牺牲少量吞吐换取可解释性；确认安全后再单独A/B恢复异步。
4. **每一步保存model checkpoint并做sealed6最小评测。** 可先每题2条；任何一题集正确数、完整率或固定参考KL越过预注册坏线立即停止。第5步才做完整`2+2+2`。
5. **训练与模型选择看正确性，不看平均reward。** 强制记录每步mixed-correct组数、全错组丢弃数、严格正确轨迹数、固定参考KL、sealed any-correct和完整率。
6. **SQL证据修复独立离线进行。** 先证明新口径能覆盖真实组合查询路径且不会让错答案进入证据正确档，再接回在线训练；本次金丝雀不能通过放宽判题救数据量。

这套方案的目的不是立刻证明最终提升，而是用很少的GPU时间回答三个问题：去掉全错组梯度后是否还退化、固定KL能否阻止累计漂移、异步陈旧性是否有额外影响。若第1–2步sealed就下降，应立即转向纠错SFT或pairwise监督，不再用当前低成功率题池做在线GRPO。

## 证据边界与复现

- 训练汇总来自54个rollout文件的864条记录，并按完整prompt仅在内存中分组；安全输出不保存prompt或hash。
- 优化指标来自训练驱动日志。第一个更新没有独立发出完整metric行，所以“零正确步骤有梯度”为已记录的25/25，而不是声称可直接观察26/26。
- sealed6是同题前后门，不是v15/v20/v21总体随机抽样；它可用于拒绝checkpoint，不能用于估计全体准确率跌幅。
- 本报告使用精确计数表而未绘图，因为核心关系是6题前后门和108组离散构成；表格比连续趋势图更能保留小样本分母和判断边界。
- 可复现安全诊断脚本为`../scripts/diagnose_qwen38_mixed27_training.py`；聚合结果为`qwen38_mixed27_training_collapse_diagnosis_20260821.safe.json`。两者均不写出题面、gold SQL、任务身份、prompt hash、工具输出或服务器路径。
