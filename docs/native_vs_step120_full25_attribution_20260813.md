# 原生 Qwen3.6-27B 与 Step 120 的完整 64 题归因

日期：2026-08-13

## 结论先行

类似“奖励黑客”的高过程分错答、反复环境探索和长程工具消耗，在原生 Qwen3.6-27B 中已经大量存在，不是 Step 120 训练新制造的。完整 25 次工具反馈协议下，原生模型有 `13` 题属于 `result_wrong_process_ok`，Step 120 为 `8` 题；原生还产生更多工具调用、重复 Bash 和更长的推理总量。现有证据不支持训练放大这种代理错配。

Step 120 也不是无条件改善。它把 numeric correct 从 `5/64` 提高到 `7/64`，严格 correct verdict 从 `2/64` 提高到 `5/64`；但进入可识别只读 SQL 的任务从 `30/64` 降到 `23/64`，完整回答从 `40/64` 降到 `35/64`，老板平均总奖励从 `0.2858` 降到 `0.2612`。更准确的归因是：训练没有创造奖励黑客行为，却出现了“少数正确率提高、查询覆盖和完成率下降”的方向性权衡。

64 题样本下，首 SQL 覆盖、完成、正确数和总奖励的配对差异都未达到双侧 `p<0.05`。因此不把方向性退化写成统计确定因果，但也不能据此继续训练或晋级 Step 120。

## 公平协议与权重身份

两侧均使用同一 64 个 current-definition 任务、相同 prompt、greedy `n=1`、48K 上下文、最多 26 个 assistant 回合和 25 次工具反馈，均为 forward-only。

- 原生侧明确跳过 actor→rollout 权重同步，直接使用原始 HF 权重；
- Step 120 侧明确执行 dist checkpoint 的 actor→rollout 强制同步；
- 两次运行均 `exit 0`、`64/64` 行落盘；
- 老板原版 `reward_judge.py` 两侧均 `64/64` 成功匹配，无 verifier error。

这修复了此前未同步 vLLM 导致的 Step 120 自由回放归因漏洞。

老板总奖励逐题比较为 Step 120 `10` 胜、`14` 负、`40` 平，双侧 exact sign `p=0.5413`。

## 首 SQL 逐题转移

两侧都有已观测首 SQL的题为 `17`；仅原生有的为 `13`，仅 Step 120 有的为 `6`，两侧都没有的为 `28`。其中 `11` 题从原生首查错误转为 Step 120 无 SQL，`6` 题反向转入首查错误；另有 `2` 题从原生首查正确/等价转为 Step 120 无 SQL。覆盖方向偏向原生，双侧 exact McNemar/sign `p=0.1671`，不足以作 0.05 水平确定性结论。

完整回答配对为两侧都完整 `30`、仅原生 `10`、仅 Step 120 `5`、两侧都不完整 `19`，`p=0.3018`。numeric correct 配对为两侧都正确 `3`、仅原生 `2`、仅 Step 120 `4`、两侧都不正确 `55`，`p=0.6875`。

## 决策与下一训练目标

Step 120 完整运行仍只得到 `22` 个合格首错 SQL pair，低于冻结门槛 `48`；不降低门槛、不把无 SQL 或未观测工具调用伪造成 rejected，当前不启动 optimizer。

下一训练目标从“继续加 SQL 正确性”改为“以原生模型为行为锚点，修复查询启动与完成，同时保住 Step 120 已出现的少数正确率收益”。任何后续 checkpoint 必须在相同 64 题完整协议上同时达到：

- 进入可识别 SQL 的任务至少 `30/64`；
- 完整回答至少 `40/64`；
- numeric correct 至少 `7/64`；
- 老板平均总奖励至少 `0.285840625`；
- `result_wrong_process_ok` 不超过 `8/64`。

这是取两侧较优维度构成的 Pareto 门禁。原生模型和 Step 120 本身都不能通过；只有同时消除覆盖回退并保留正确性收益的新模型才允许晋级。仓库新增可执行门禁，候选必须五项全过，且门禁本身不授权追加训练。
