# 单书CPT“Logistika提升9个多点”调查

日期：2026-09-23。只读调查5号机，下载必要证据后离线复算；没有启动模型、改动远端评分或训练。

## 结论

**找到了能重现“提升9个多点”的比较，但它混用了新旧评分口径，不能作为CPT收益。** 指定模型确实在另一套评测中得到75.17%；旧Step120显示65.42%，相差9.75个百分点。但相同Step120原始输出统一重打分后为75.24%，CPT反而少1题。我们9月3日的同口径结果为81.54%→81.40%，少2题，记忆没有遗漏一次9点增益。

没有观察到老板当时查看的表或操作，不能断言其确切比较对象。下列证据支持一个具体解释：**基线旧解析器造成约9.8点低估，9月21日修复了8K汇总，但30K派生目录仍保留旧分数。** 相比原生模型的旧分数也会显示约9.6点，因此仅凭“9个多点”不能区分当时比较的是原生还是Step120。

## 9点来自哪里

旧 `scripts/eval/scorers/multichoice_scorer.py` 使用正则 **`[A-J]`**，从预测和金答案中提取字母集合。这不支持本数据的完整候选编号：除K以后字母外，305道269选项题还使用连续字符编号，包含标点、控制字符和扩展Unicode字符。

旧Step120记录中261题提取为空。对**同一份回答**重新打分后：

| 仅评分变化 | 数量 |
|---|---:|
| 旧错→新对 | 145 |
| 其中旧答案提取为空 | 145 |
| 其中属于269选项题 | 139 |
| 旧对→新错 | 3 |
| 净增加正确 | 142（+9.8202点） |

所有旧/新金答案逐条相同。旧评分可从原始输出用旧正则完整复现；这些变化不需要训练、重推理或改答案。旧规则也可能因丢弃范围外字符而误判为对，所以并非简单“补回145题”而没有反向修正。

作为交叉检查，将同一旧规则离线套到CPT已有回答得到948题；与Step120旧规则946题相比也仅多2题（+0.14点），同样不存在9点增益。这是本次重算，非伪称找到了一次历史CPT旧评分运行；旧规则有缺陷，不建议采用。

新数据的1,446条记录均配置 `extract_method=answer_or_raw`、`score_method=exact_match`；实际 `score.py` 优先按这些逐题字段路由。即使配置快照还写着 `scorer: multichoice_scorer`，也不能据此认定实际仍走旧A–J评分。这是核查执行代码而不只看配置名的关键。

## 为什么现在还可能看到9点

8K的Step120汇总写明 `rescored: 2026-09-21_dual_unify`，保留旧值 `accuracy_pre_dual_unify`，并有 `scores_pre_dual_unify.jsonl` 可复算。

然而30K目录标记 `derived_from_8k=true`，预测文件SHA256与对应8K逐字节相同，**并非另跑30K**。当前其基线汇总仍是旧值：

| 展示目录 | Step120-opensource | 单书CPT | 表面差值 |
|---|---:|---:|---:|
| `nothink_8192` | 75.24% | 75.17% | −0.07点 |
| `nothink_30720`（派生复制） | 65.42% | 75.17% | +9.75点 |

基线两目录预测相同、分数不同，已经直接证明存在陈旧汇总。已只读查看看板：`dashboard/serve.py` 按目录读取 `summary.json`，前端标识30K复制结果，但没有证据证明老板当时选择了该档位。本次没有替对方修改看板或结果文件。

## 他怎么评，我们怎么评

| 项目 | 另一套9月20日CPT评测 | 我们9月3日评测 |
|---|---|---|
| 题库 | LogistikaBench全1,446题 | 同1,446题 |
| 提示/回答编号 | 字符编号，要求输出答案字符串 | 零基数字索引JSON |
| 评分 | 逐题字段驱动答案提取及字符串评分 | 解析JSON后答案集合完全匹配 |
| 示例 | 0-shot | 0-shot |
| 采样 | temperature=0，关闭thinking | 相同 |
| 最大输出 | 8,192 tokens | 128 tokens |
| CPT启动脚本 | vLLM-Ascend 0.23.0rc1，BF16，TP4×DP4 | 0.22.1rc1，BF16，TP4×DP2 |
| 结果 | Step120 1088→CPT1087 | Step1201179→CPT1177 |

另一套两模型保存的全部1,446条提示均与当前处理文件逐条一致；与我们输入核对，1,444条按字符选项格式重建后逐字一致，另2条只有空白差异，全部题目、选项和金答案完成映射。**不是少测/多测题目导致差异。**

另一套Step120快照明确 `mtp: true`；CPT供应链脚本没有MTP启动参数。后来全套其他benchmark的脚本有MTP，不能套用到这次供应链记录。历史容器已不在，服务细节依据保存脚本/配置，不能声称完整复原了运行时环境。

主比较两模型全部输出以stop结束，没有长度截断；因此不支持用“我们128 token不足、他们8K更长”解释9点。两种协议下绝对分数约81%与75%的差异，混合了提示、编号、解析和服务设置，尚未逐因素隔离，不能只归因于其中一个。

我们的9月3日原始输出也重新解析了：Logistika Step1201179、CPT1177，5修复/7损失，与[当时报告](qwen36_step120_logistics_single_book_cpt_20260903.md)一致。两套历史结果都不支持单书CPT带来9点知识增益。
